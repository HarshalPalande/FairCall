# AI Risk Manager — Chargeback Evidence Copilot

**Razorpay Buildathon — Track 02: AI Risk Manager**
Scoped to **one** reason code: Visa **13.1** — "Merchandise / Services Not Received."

> **Read this first (90 seconds).**
> This system decides, for each disputed payment, whether contesting it is worth
> the money — and hands everything else to a human with the reasoning attached.
> It auto-handles **56% of disputes**, at a disclosed **14.2% false-positive rate**
> on that auto path, and beats blindly contesting everything by **₹311,973** across
> 3,000 disputes — almost entirely by *not paying an analyst to do what didn't need
> a human*.
>
> **All data here is synthetic**, generated by a seeded script in this repo. That was
> deliberate: the honest alternative was repurposing a fraud dataset that has no
> dispute win/loss labels and quietly calling its proxy labels ground truth. Synthetic
> data lets us publish the exact data-generating process and reproduce every number
> from a cold clone. What it does **not** do is prove real-world accuracy — so read
> every metric below as *"the system design works, measured against a world we
> disclosed in full,"* not as a benchmarked chargeback model. Swapping in real dispute
> outcomes is the explicit next step (`buildathon.md` §7, Phase 2), and nothing about
> the architecture changes when you do.

## What this is

A detector + verifier for a single, tractable slice of the chargeback problem. Given a
dispute (transaction + whatever evidence the merchant has on file), the system:

1. Scores calibrated win probability if contested (XGBoost + isotonic calibration).
2. Scores evidence completeness against a rule-based checklist for this reason code —
   this part has **no ML in it** and is useful on its own.
3. Ranks which single missing piece of evidence would move the win probability most
   (counterfactual re-scoring against the same calibrated model).
4. Computes the actual expected-₹-value of contesting vs. accepting, and only
   recommends auto-contest when EV favors it **and** the amount is under a hard,
   non-overridable ceiling **and** evidence is complete enough. Otherwise it escalates
   to a human with the full picture attached.
5. Logs every decision to an append-only, hash-chained audit log.

**Where the LLM is:** the brief allows "detector or verifier or auto-responder." The
core system above is detector + verifier, and it contains no LLM at all — that was
deliberate, to keep the narrow thing solid. A grounded evidence-draft step
(`src/evidence_draft.py`) is included separately as a clearly-labelled **prototype**:
it is not wired into the decision path, it is human-gated, and it is built so the model
is the least-trusted component — see the dedicated section below.

## Dataset — read this before looking at any metric

**All data in this repo is synthetic**, generated by `src/data_gen.py` with a fixed
seed. This was a deliberate choice, made explicit here rather than left implicit:

- We considered reframing IEEE-CIS (a *fraud-detection* dataset) as chargeback
  outcomes, but that dataset has no actual win/loss labels for contested disputes —
  doing so would mean presenting a proxy as ground truth without saying so.
- Fully synthetic data lets us **disclose the exact data-generating process**
  (see the docstring in `src/data_gen.py`), guarantee reproducibility, and encode the
  specific loss root-causes named in the brief (missing evidence, weak evidence, late
  filing, genuine unwinnable fraud) so the model has real, inspectable structure to
  learn — instead of us hand-waving about "realistic" data we can't actually justify.

**Every metric below is a metric against synthetic ground truth. It is not a claim
about real-world dispute-win-rate performance.** Treat this repo as a demonstration of
the *system design* — split discipline, calibration, EV-based decisioning, audit —
not as a benchmarked fraud/dispute model.

## Architecture

```
Razorpay payment.captured webhook
    |
    v
Transaction --> Dispute Prevention Score (XGBoost, txn-time features only)
                  |-- HIGH/MEDIUM risk --> "collect evidence now" alert to merchant
                  |-- LOW risk         --> standard monitoring

Razorpay payment.dispute.created webhook
    |
    v
Dispute (10.4) --> CE3.0 Qualification Engine (deterministic rules, zero ML)
                     |-- QUALIFIES     --> blocked pre-emptively, liability shifts
                     |                     to issuer, never enters the VAMP ratio
                     |-- DOES NOT QUAL --> standard representment path

Dispute (13.1) --> Feature Store (UID aggregates, causal/past-only)
        --> XGBoost Detector --> Isotonic Calibrator
        --> Evidence Completeness Checker (rule-based, standalone)
        --> Counterfactual Engine (what evidence would help most?)
        --> Four-Way Decision Engine (EV + VAMP portfolio cost)
              |   guardrails first, and absolute:
              |     hard ₹ ceiling  -> gates ALL automated actions
              |     evidence gate   -> gates CONTEST only
              |
              |-- DEFLECT       Order Insight, pre-dispute      (no VAMP impact)
              |-- AUTO_RESOLVE  RDR refund                      (no VAMP impact if non-fraud)
              |-- CONTEST       representment                   (VAMP already incurred)
              |-- ESCALATE      Human Review Queue  <-- fallback when no automated
                                                       action is permitted; never
                                                       EV-scored against the others
        --> Grounded Evidence Draft (PROTOTYPE, human-gated, not in decision path)
        --> Audit Trail (hash-chained, append-only)
        --> SHAP Explainability (validates feature importance, see below)
```

`app/pages/3_Razorpay_Integration.py` demonstrates the webhook mapping above end to
end against real Razorpay payment-object shapes (sample data by default, live Test
Mode API if `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` are set) — see the dedicated
section below.

See `buildathon.md` for the full-scope design (grounded LLM, merchant intelligence
hub, etc.) — that document is the north star and marks what is and isn't built;
this repo is the deliberately-cut subset of it that's actually built and tested.

## The train/calibration/test split — why it's not a random shuffle

Chargeback data has temporal structure: fraud rings evolve, merchant ops change,
category mix shifts seasonally. A random shuffle split would let the model implicitly
see the future during training and overstate performance. Instead (`src/model.py`,
`time_respecting_split`) the data is sorted by `dispute_date` and cut into three
**contiguous, non-overlapping** blocks — train (70%) → calibration (15%) → test (15%).
Calibration is fit on its own slice, not train or test, so the test-set reliability
numbers aren't contaminated by the isotonic regressor having seen those rows.

The per-customer ("UID-style") aggregate features in `src/features.py` are computed as
**expanding, strictly-past-only** statistics — a dispute at time T only ever sees that
customer's disputes with `dispute_date < T`. Computing these over the full dataset
first (a common mistake) would leak future win-rate backward into earlier rows.

## False-positive cost analysis (`artifacts/metrics.json` → `false_positive_analysis`)

The rubric explicitly asks for "honest metrics including false-positive cost," not just
a false-positive rate. A false positive here is: the system said `AUTO_CONTEST`, but the
merchant actually lost — so they eat the ₹500 contest cost *on top of* the chargeback
amount, for nothing.

On the same 3,000-row held-out test slice:

| Metric | Value |
|---|---|
| Auto-contested | 1,687 (56.2% of test disputes) |
| True positives (auto-contested, actually won) | 1,448 |
| False positives (auto-contested, actually lost) | 239 (14.2% of auto-contested cases) |
| Value recovered by true positives | ₹2,627,453.63 |
| Cost of false positives | ₹890,988.14 |
| Net value of auto-decisions | ₹1,736,465.49 |

## Backtest — simulated ₹ impact of 3 strategies

`src/backtest.py` compares, over the same test slice: (1) accepting every dispute, (2)
blindly contesting every dispute, and (3) this system (EV-based auto-contest, with
escalated cases going to a simulated human analyst who contests the strongest
`human_contest_rate` = 70% of them, by win probability, and accepts the rest outright).
**That 70% figure, and the ₹200/case analyst labor cost below, are stated assumptions,
not measurements** — in production both would be measured from actual analyst
behavior and ops time-tracking, and the backtest is disclosed as sensitive to them.

An earlier version of this backtest priced "Contest All" as if evidence packets
assemble themselves for free — it doesn't. Preparing a contest response takes a human's
time even when the system doesn't need one (an `AUTO_CONTEST` case genuinely doesn't;
a human blindly contesting every dispute does). `ANALYST_LABOR_COST_PER_CASE_INR` = ₹200
is now charged per case to any strategy that requires manual packet prep — that's
"Contest All" on every case, and "This System" only on the escalated cases a human
analyst decides to actually contest:

| Strategy | Net ₹ outcome |
|---|---|
| Accept all (no contest) | −₹6,683,196.06 |
| Contest all (no intelligence, ₹200/case labor on all 3,000 cases) | +₹773,874.16 |
| This system (EV-based, ₹200/case labor on 919 analyst-contested cases only) | +₹1,085,847.50 |

With labor priced honestly, this system now beats blind Contest-All by **₹311,973.34**,
not because of smarter EV math on the auto-handled cases (that mechanism is unchanged
from before), but because **56% of cases (1,687 of 3,000) are auto-resolved with zero
analyst time** — ₹416,200 of labor that Contest-All would have spent regardless of
whether a human's judgment was actually needed. That's the real, disclosed source of
the value: not better win-rate prediction, but not paying a human to do what didn't
need a human. Regenerate with `make backtest`; chart at
`artifacts/backtest_comparison.png`.

**These ₹ figures price the contest-vs-accept decision only — VAMP is deliberately
excluded, and that is a scope statement, not an oversight.** `src/backtest.py` scores
every case through the original two-way engine (`AUTO_CONTEST` / `ESCALATE`), the same
one `EV(contest)` / `EV(accept)` in the table above comes from. It does not call
`decide_four_way()`, so DEFLECT and AUTO_RESOLVE — and the VAMP cost that makes
AUTO_RESOLVE the right call in [case 4 of `make demo`](#beyond-contest-or-accept-the-four-way-decision-engine)
even at a 69% win probability — never enter these three numbers. Reproducing a
VAMP-aware version of this backtest means simulating the portfolio's dispute-event
count sequentially across all 3,000 test cases, since headroom (and therefore marginal
VAMP cost) changes with every case decided before it — a materially different
simulation from scoring each case independently, and one this backtest does not
attempt. The four-way engine's actual ₹ effect is demonstrated per-case in `make demo`
and, at the portfolio level, in the RDR Optimizer page (`app/pages/7_RDR_Optimizer.py`),
not here.

## Dispute Prevention Score — proactive risk flagging

Every reactive system in this space, including the detector above, only sees a dispute
*after* it's filed. This is a second, independent model that scores **transactions at
payment time**, before any dispute exists, to answer: "will this become a dispute
within 30 days?" A merchant with a HIGH-risk transaction can proactively collect
delivery proof before it's needed — prevention is cheaper than cure, and the best
dispute to win is the one that never happens.

This model is trained on strictly less information than the outcome detector: no
evidence flags (evidence doesn't exist yet), no `late_filing`, no dispute-history
aggregates — only what's known at the moment of payment (amount, category, device,
shipping method, day of week, month). Its metrics are honestly, and expectedly, weaker:

| Metric | Prevention model | Outcome detector (for comparison) |
|---|---|---|
| ROC-AUC | 0.658 | 0.876 |
| PR-AUC | 0.353 | 0.938 |
| Base rate (positive class) | 21.9% | 71.6% |

**Disclosed modeling assumption:** the synthetic "normal" transaction background this
model is trained against is deliberately biased so that higher-value, express-shipped,
electronics/digital-goods purchases carry somewhat higher dispute propensity than
routine grocery/home purchases on standard shipping (`src/prevention.py`,
`build_transaction_dataset`). This is a directionally plausible prior we chose, not a
pattern measured from real data — said outright so the 0.658 ROC-AUC isn't mistaken for
a validated real-world number. An earlier version of this generator gave the two
populations *identical* transaction-time distributions, which produced a 0.50 ROC-AUC —
a coin flip. We caught that before writing it up, because presenting noise as "the
innovation" would have failed the same bar as everything else in this README.
Regenerate via `make train`; category-risk chart at
`artifacts/prevention_category_risk.png`.

## SHAP feature importance

`src/model.py` runs `shap.TreeExplainer` over the held-out test slice at the end of
training and saves a summary plot to `artifacts/shap_summary.png`. The honest result,
by mean |SHAP value|: **`cust_prior_win_rate` (a customer-trustworthiness proxy) is the
single strongest individual feature**, with the three required reason-code-13.1
evidence flags (`has_delivery_confirmation`, `has_tracking_number`, `has_signed_pod`)
clustered immediately behind it — ranked #2, #3, #4 out of the full feature set.

We're stating it this way rather than claiming evidence "dominates" outright, because
it doesn't dominate as a single top feature — customer history does, in this synthetic
world.

**The obvious objection, checked rather than hand-waved.** The generator couples
customer trust to evidence availability (`evidence_base_rate = 0.35 + 0.5 * trust` in
`src/data_gen.py`), so the natural suspicion is that `cust_prior_win_rate` and evidence
completeness are the same signal wearing two hats, and SHAP is just ranking a confound.
We measured it on the full 20,000-row generated set:

| Correlation | Value |
|---|---|
| `cust_prior_win_rate` ↔ evidence completeness | **0.059** |
| `cust_prior_win_rate` ↔ won | 0.467 |
| evidence completeness ↔ won | 0.276 |

They are **effectively uncorrelated with each other** (0.059) while each independently
predicts the outcome. The coupling through `trust` exists in the generator but is
swamped by per-dispute noise and by `cust_prior_win_rate` being a small-sample estimate
of trust. So this is not one signal counted twice — it is two independent signals, and
the model uses both. Evidence completeness alone moves the win rate monotonically:

| Evidence completeness | Win rate | n |
|---|---|---|
| 0% | 36.2% | 1,651 |
| 33% | 62.1% | 5,485 |
| 67% | 77.2% | 7,522 |
| 100% | 83.1% | 5,342 |

What SHAP validates, then, is that the three evidence flags the rule-based Evidence
Completeness Checker (`src/evidence.py`) already treats as required for reason code
13.1 are independently among the model's most influential inputs — the rule-based
checker's design and the model's learned behaviour agree on what matters, without
either being a restatement of customer history. Reproduce the table above with
`make train`; the correlations are a three-line computation over
`build_feature_frame()`.

- **Demo mode by default** (4 realistic sample payments, no credentials needed); **live

## The EV Decision Engine — the actual differentiator

Not a confidence threshold. `src/ev_engine.py`:

```
EV(accept)  = -amount
EV(contest) = amount * (2*P(win) - 1) - contest_cost
```

`contest_cost` = ₹150 labor + ₹350 admin fee = **₹500 flat** (see cost-table caveat
below). Auto-contest requires all three: EV(contest) > EV(accept), amount ≤ hard
ceiling (₹25,000, fixed, never overridden by confidence), and evidence completeness ≥
60%. Otherwise: escalate to a human with the score, EV math, and evidence gaps
attached.

**Cost-table honesty note:** ₹150 / ₹350 / ₹25,000 are placeholder assumptions for this
demo, set by us, not sourced from Razorpay finance/risk ops. The same applies to every
figure added by the VAMP and pre-dispute work: `ANALYST_LABOR_COST_PER_CASE_INR` (₹200),
`RDR_RESOLUTION_FEE_INR` (₹250), `ORDER_INSIGHT_COST_INR` (₹40),
`ORDER_INSIGHT_BASE_DEFLECT_RATE` (0.35), `USD_TO_INR` (88), and the simulated merchant
portfolio (`MERCHANT_MONTHLY_SETTLED_TXNS`, `MERCHANT_MONTHLY_DISPUTE_EVENTS`). We say so
here and in `src/config.py` rather than presenting them as calibrated business numbers.
In production these would come from finance ops and likely vary by merchant category.

What is **not** a placeholder: the VAMP thresholds (1.5% Excessive, 1,500-event
monitoring floor, $8/dispute penalty) and the RDR fraud/non-fraud VAMP-exclusion
asymmetry are from Visa's published program rules, not invented by us.

**A nuance we found while building this, not in the original brief:** because upside
(recovering `amount`) scales with `amount` while `contest_cost` is fixed, pure EV math
in this formula *never* disagrees with a naive "contest if win_prob > 50%" threshold —
higher stakes make contesting *more* attractive under risk-neutral EV, not less. The
actual divergence between this system and a naive threshold comes from the **hard
ceiling**, which is a deliberate risk-aversion rule sitting *outside* the EV
calculation — it exists because a business reasonably wants to be risk-averse on any
single high-stakes automated decision, even when risk-neutral EV would say to proceed.
`scripts/demo.py` case 3 shows this explicitly rather than mislabeling the ceiling's
effect as something the EV formula itself produced.

## VAMP — the cost the transaction-level EV math misses

`src/vamp.py`, `app/pages/5_VAMP_Risk.py`.

The EV engine above prices a dispute at its transaction amount. That is incomplete.
Under Visa's Acquirer Monitoring Program, every dispute also increments a
portfolio-level ratio:

```
VAMP ratio = (TC40 fraud reports + TC15 disputes) / settled CNP transactions
```

**The asymmetry that matters: the ratio counts disputes FILED, not disputes LOST.**
A merchant who contests and wins still carries that dispute in their ratio. Contesting
protects the transaction value and does nothing for portfolio standing. Only keeping the
dispute from being filed — deflection, or pre-dispute resolution — keeps an event off
the ratio.

With the simulated portfolio in `config.py` (200,000 settled txns, 2,600 dispute events
→ 1.30% against a 1.50% threshold, 400 events of headroom), the marginal VAMP cost of
one additional dispute is **₹4,576** — modelled as the portfolio-wide penalty exposure
weighted by the probability that this dispute is the one that crosses the line
(1 / headroom). It is deliberately a simple, explainable formula rather than a black box,
and it rises sharply as headroom shrinks.

**Disclosure:** the VAMP thresholds, the ₹8/dispute penalty and the monitoring floor are
from Visa's published program rules. The merchant portfolio figures and the USD→INR rate
are PLACEHOLDER simulation values, same standard as the rest of the cost table.

## Beyond contest-or-accept: the four-way decision engine

`src/decision_engine.py`. The original EV engine has two outputs, which models the
decision as "fight or don't fight." Visa's pre-dispute infrastructure gives four
meaningfully different levers, and they differ in **both** cost and VAMP consequence:

| Action | What it does | Counts toward VAMP? |
|---|---|---|
| `DEFLECT` | Order Insight — push order detail at cardholder inquiry, before a dispute exists | **No**, if it works |
| `AUTO_RESOLVE` | RDR — refund the cardholder pre-dispute per merchant rules | **No** for non-fraud codes; **yes** for fraud code 10.4 |
| `CONTEST` | Representment — the original path | Yes, already filed |
| `ESCALATE` | Human analyst review | Yes, already filed |

The consequence a two-output engine cannot express: **for a non-fraud dispute,
deliberately refunding via RDR — even one you would probably WIN at representment — can
be the cheaper decision**, because it keeps the event off the VAMP ratio entirely. The
engine surfaces that case explicitly in its reasoning rather than leaving you to notice it.

`make demo` runs all four demo cases through both engines side by side, not just this
one — see case 4 (69% win probability) in the [verified cold-clone run](#verified-cold-clone-run)
above for the live version of the paragraph you just read.

### Why `ESCALATE` is not scored against the other three

This is the design decision in the module, and it is a safety property, not a style
preference.

An earlier design gave `ESCALATE` an expected value (the accept-loss) and picked
`max(EV)` across all four actions. That is broken in a way that passes tests.
`DEFLECT`'s EV is a convex combination of "cheap success" and "the accept loss", so it
**dominates a flat accept-loss whenever deflection has any chance of working**. Priced
that way, ESCALATE loses essentially always — and a ₹42,000 over-ceiling dispute gets
routed to `DEFLECT`, an automated action, instead of to a person. The hard-ceiling
guarantee disappears silently, while a test asserting only `chosen != CONTEST` still
goes green, because the action genuinely isn't CONTEST — it's a *different* automated one.

So the structure here is: **`ESCALATE` is the fallback, not a competitor.** The engine
picks the best viable *automated* action; if no automated action is permitted, the case
goes to a human. That makes the guardrail structural rather than arithmetic.

### Which guardrail gates what, and why they differ

| Guardrail | Gates | Reasoning |
|---|---|---|
| Hard ₹ ceiling | **All three automated actions** | "No single large automated decision without a human" is a property of the *amount*, not of which lever you pull. Auto-refunding ₹150,000 is exactly as much a large automated money movement as auto-contesting it. |
| Evidence minimum | `CONTEST` only | It is a statement about the strength of the case you would argue, not the amount at risk. It deliberately does **not** gate `AUTO_RESOLVE`: refunding is the conservative action, and thin evidence is a reason to refund rather than fight — precisely the lever the two-output engine lacked. |

`tests/test_decision_engine.py` asserts the property rather than a proxy: a parametrised
sweep over amounts, win probabilities, evidence levels, both reason-code classes and
both order-data states confirms **no over-ceiling case is ever automated**, and a
regression test pins demo case 3 (64%, ₹42,000) to `ESCALATE` while confirming its
contest EV genuinely was favourable — otherwise the case proves nothing.

## RDR Rule Optimizer

`src/rdr_optimizer.py`, `app/pages/7_RDR_Optimizer.py`.

Visa permits a limited number of merchant-configured RDR rule scenarios. Given a dispute
distribution and current VAMP headroom, what amount threshold minimises **total** cost —
refund outlay plus VAMP exposure plus representment costs?

That is a real trade-off: auto-resolving more disputes costs more in refunds but buys
back VAMP headroom; auto-resolving fewer preserves revenue but risks crossing the
Excessive threshold, which applies penalties to the merchant's *entire* dispute volume
rather than just the marginal case. The optimizer sweeps candidate thresholds and returns
the **full cost curve**, so the trade-off is inspectable rather than hidden behind one
recommended number.

Two disclosed modelling choices, because the output is a ₹ recommendation:

- **The sweep is capped at the hard ceiling.** RDR is an automated money movement and is
  bound by the same rule as every other automated action. A sweep recommending
  auto-refunds above ₹25,000 would be recommending something the decision engine refuses
  to execute.
- **Escalated disputes are priced as accepted losses** — a deliberately pessimistic
  floor, not a prediction, since a human analyst would contest some of them. The
  remaining-slice cost is therefore an upper bound, which biases the optimizer mildly
  *toward* auto-resolving. `src/backtest.py` models analyst behaviour explicitly; this
  module does not.

## CE3.0 qualification engine

`src/ce3.py`, `app/pages/6_CE3_Qualification.py`. A deterministic, zero-ML rules engine
for Visa Compelling Evidence 3.0: ≥2 prior undisputed transactions 120–365 days before
the dispute, ≥2 data elements matching across them, at least one of which must be IP
address or device ID. Qualification blocks the dispute pre-emptively and shifts liability
to the issuer — so the event never touches the VAMP ratio.

**Scope, stated plainly:** CE3.0 applies to reason code **10.4** (Fraud — Card Absent),
not the 13.1 this project is scoped to. It is here to show the rule-engine pattern
extending to a second reason code, not as a claim that it applies to the main pipeline.
Deterministic by design: a compliance-adjacent feature has to explain exactly *why* a
dispute did or did not qualify, not hand back a probability.

## The three demo cases (`make demo`)

1. **Clear auto-contest** — high win probability (93%), complete evidence, ₹1,800 →
   `AUTO_CONTEST`.
2. **Clear escalate** — low win probability, zero evidence on file → `ESCALATE`
   (blocked on evidence completeness, not just probability). Counterfactual shows
   adding a tracking number would move win probability 17% → 30%.
3. **The moment that matters** — 64% win probability, ₹42,000 → EV math alone still
   favors contesting, but the hard ₹25,000 ceiling escalates it to a human anyway. A
   naive fixed-threshold system would have auto-acted here; this system doesn't.

## Evidence Completeness Checker — the litmus test

*"If the ML model disappeared tomorrow, would this still be useful?"* `src/evidence.py`
answers that on its own: given reason-code-13.1's required documents (tracking number,
delivery confirmation, signed POD) and a few consistency rules (e.g. a signed POD can't
exist for a digital-delivery order), it flags missing/inconsistent evidence with zero
ML involved. The EV engine and counterfactual engine both consult it before any model
score matters.

## Grounded evidence draft — the LLM, kept on a leash (PROTOTYPE)

`src/evidence_draft.py`. Labelled a prototype because it is one: it is not wired
into the EV engine's decision path, and nothing in this system submits anything
anywhere.

An LLM asked to write a chargeback rebuttal will produce a fluent, confident letter
asserting the parcel was delivered and signed for — whether or not any of that is
true. In a dispute response that isn't a bad sentence, it's a false representation to
a card network. So this component is built on the assumption that **the model is the
least trustworthy part of it**:

1. **Fact ledger** — a closed set of atomic facts built from the dispute. It contains
   *only* evidence actually on file; absent evidence produces no fact. The model never
   sees the raw case, so there is no gap for it to write around. Facts that hurt the
   merchant (late filing) are included — an honest ledger isn't a sales document.
2. **Constrained generation** — the model may return exactly one thing: a list of
   claims, each citing ledger fact IDs. It does not write the letter. Every greeting,
   heading and sign-off in the output is boilerplate from `render_letter()`. Shrinking
   the model's output surface is what makes the output checkable.
3. **Verification** — pure Python, no model, no network. A draft is **rejected, not
   repaired**, if it cites a fact that doesn't exist, makes an uncited claim, or
   asserts something the ledger can't support. That last check is the one that matters:
   it catches a claim carrying a *valid* citation while asserting more than the cited
   fact shows (e.g. "signed for on delivery" when no signed POD is on file).
4. **Human gate** — an approved draft is still a draft, and says so in the text.

**Disclosed limitation:** the verifier checks citation validity and scans for
assertions whose supporting evidence type is absent. It does **not** do semantic
entailment — a claim citing a real fact but overstating what that fact shows would
pass. Closing that needs a second-pass entailment check, which is not built. The
keyword scan is a floor, not a proof, and it's stated here rather than left for a
reviewer to find.

The ledger and verifier have no API dependency, so `tests/test_evidence_draft.py`
(19 tests) runs with no key and no network — the adversarial cases are written as
"what would a hallucinating model produce." With no `ANTHROPIC_API_KEY` set, the
component degrades to `UNAVAILABLE` and the rest of the pipeline is unaffected; it
never invents a letter. Model: `claude-opus-5` via the official `anthropic` SDK.

## Audit trail — an actual hash chain, not a decoration

`src/audit.py` appends one JSON line per decision to `audit_log/decisions.jsonl`. Each
entry's `entry_hash = sha256(prev_hash + canonical_json(body))`. `verify_chain()`
recomputes every hash from the stored body and `prev_hash` and checks it matches — this
detects tampering with, reordering, or deletion of any past entry, which a hash of only
the current entry (no `prev_hash`) would not catch. Run `make demo` and check the final
line of output for a live chain verification.

That's the happy path, which a log with no chaining at all would also pass — so
**`make tamper-demo` shows the other half**: it writes three decisions, rewrites one of
them the way someone hiding a bad call would (`ESCALATE` on ₹42,000 → `AUTO_CONTEST` on
₹9,000), and re-verifies. The chain reports the exact line and reason, and appending
further valid entries on top does not heal it. `tests/test_audit.py` asserts the same
for deletion and reordering.

## Tests

124 tests across 10 files, run with `make test`:

- `tests/test_ev_engine.py` (8) — the EV formula computed by hand, the hard ceiling
  blocking even at 99% confidence, the evidence-completeness gate blocking
  otherwise-favorable EV, the same win-probability flipping the decision purely on
  amount (ceiling), input validation on out-of-range probabilities/negative amounts.
- `tests/test_evidence.py` (6) — completeness scoring at 0%/partial/100%, and the
  digital-delivery / signed-POD-without-tracking-number consistency rules.
- `tests/test_prevention.py` (5) — the prevention dataset holds both classes at the
  right ratio and stays time-sorted, and its features contain **no** evidence flags or
  dispute-outcome columns (the whole point of testing this: transaction-time features
  only, no leakage from information that doesn't exist yet at payment time).
- `tests/test_backtest.py` (6) — false-positive costing by hand, Accept-All's raw loss,
  and — directly testing the Feature 1 fix above — that Contest-All bears analyst labor
  on every case while `AUTO_CONTEST` cases bear none.
- `tests/test_audit.py` (8) — the tamper claims, executed: an edited body, a deleted
  entry, and two swapped entries are each detected, and appending valid entries on top
  of a tamper does not heal it. The deletion and reorder cases are the ones a
  per-entry hash with no `prev_hash` would silently pass, which is the whole reason
  the log is chained.
- `tests/test_pipeline.py` (10) — the end-to-end product, not its parts:
  `score_dispute()` returns a complete result, its evidence numbers match the
  standalone rule-based checker exactly, more evidence raises win probability, the
  evidence gate and the ₹ ceiling each flip the decision through the real pipeline,
  counterfactuals are only offered for evidence the merchant lacks and come back
  ranked, and every scored decision lands in the audit log as a verifiable chained
  entry (and writes nothing when `write_audit=False`, which is how the backtest scores
  3,000 disputes without polluting the log). Trains its own small model in a fixture,
  so it runs on a cold clone with no `make train`.
- `tests/test_decision_engine.py` (48) — the four-way engine (CONTEST / DEFLECT /
  ACCEPT / ESCALATE) and the RDR threshold optimizer. The guardrail tests assert the
  safety **property**, not a proxy for it: an earlier design scored ESCALATE against the
  automated actions on expected value, so an over-ceiling dispute was routed to DEFLECT —
  still an automated action, just not CONTEST. A test asserting `chosen != CONTEST` passes
  happily against that bug, so these assert `chosen == ESCALATE`, which is what the hard
  ceiling actually promises. A 27-case parametrised sweep (3 amounts x 3 win probabilities
  x 3 completeness levels) pins that **no** over-ceiling case is automated at any
  combination. The RDR half covers the cost curve, that the optimizer never recommends a
  threshold above the hard ceiling, that non-fraud RDR buys back VAMP headroom while fraud
  codes buy back none, and the empty-frame edge case.
- `tests/test_evidence_draft.py` (19) — the fact ledger and the verifier: what the model
  is allowed to **know**, and what it is allowed to **say**. Neither touches the network
  nor needs an API key, which is the point — the LLM is the untrusted component here and
  the guardrails around it are pure functions, so they can be tested exhaustively and
  cheaply. The adversarial cases are written as "what would a hallucinating model
  produce": a fabricated citation, an uncited claim, and an assertion the ledger cannot
  support (parametrised across all four assertion patterns), plus one bad claim failing
  the whole draft and rejected drafts never carrying letter text.
- `tests/test_ce3.py` (8) — the CE3.0 qualification rules engine: two matching priors
  inside the window qualify, while a wrong reason code, priors too recent, priors too old,
  a disputed prior, or only one prior each reject. An IP or device anchor is required, and
  the same input always produces the same output.
- `tests/test_vamp.py` (6) — the VAMP ratio computed by hand, the excessive flag at the
  threshold boundary and below it, zero VAMP cost below the monitoring floor, marginal
  cost rising as headroom shrinks, and the flat penalty an already-excessive merchant pays.

## Defense-only enforcement

| Constraint | Enforcement |
|---|---|
| No fabricated evidence claims | Enforced by `src/evidence_draft.py`: the model only ever sees a fact ledger built from evidence actually on file, may only emit claims citing ledger fact IDs, and a pure-Python verifier rejects any draft with a fabricated citation, an uncited claim, or an assertion the ledger can't support. Prototype, human-gated — and see the disclosed entailment limitation in that section. |
| No unbounded autonomy | EV engine's only two outputs are `AUTO_CONTEST` or `ESCALATE` — nothing else, enforced by the `Action` enum. |
| Hard ₹ ceiling | Fixed constant in `src/config.py`, checked independently of model confidence; cannot be bypassed by the model. |
| No autonomous submission | This demo does not submit anything anywhere — `AUTO_CONTEST` means "recommend contesting," not "submit." A production build would still gate on human review before submission, per `buildathon.md`. |
| No customer contact | Not implemented; nothing in this system messages the disputing customer. |
| Full reversibility | Every scored decision, including its EV math and evidence gaps, is logged before any downstream action would occur. |

## What we built vs. what we deliberately didn't (and why)

**Built, tested, working:**
- Synthetic dataset generator scoped to one reason code, fully disclosed
- Feature store with causal (past-only) per-customer aggregates
- XGBoost detector on a time-respecting split
- Isotonic calibration + reliability diagram
- Rule-based Evidence Completeness Checker
- Counterfactual re-scoring / evidence-impact ranking
- EV Decision Engine with an explicit, disclosed cost table and hard ceiling
- False-positive cost analysis with real ₹ figures (rubric requirement, not just a headline FP rate)
- Backtest simulation across 3 strategies, with honest labor-cost accounting and every
  result disclosed, favorable or not
- Dispute Prevention Score — a second, honestly-weaker model scoring transactions at
  payment time, with a disclosed correction after an earlier version scored a coin flip
- Human Review Queue ranked by recovery value
- Razorpay payment integration (sample data by default; live Test Mode API when credentials are set)
- SHAP feature importance, validating the evidence-completeness features against what the model actually learned
- Cost Sensitivity Dashboard — interactive parameter tuning, not hardcoded assumptions
- Append-only, hash-chained audit log with a real verification function, plus a
  `make tamper-demo` that edits a logged decision and shows the chain catching it
- Streamlit analyst UI: 5 pages (dispute copilot, prevention score, review queue, Razorpay integration, cost sensitivity)
- 124 tests across 10 files, including end-to-end pipeline tests and executed tamper,
  deletion and reorder cases for the audit chain

- Grounded LLM evidence draft (**prototype**) — fact ledger + constrained generation +
  a pure-Python citation/unsupported-assertion verifier that rejects rather than
  repairs, human-gated and never submitted
- VAMP portfolio-risk model — the cost the transaction-level EV math misses, with the
  disputes-filed-not-lost asymmetry made explicit
- Four-way decision engine — DEFLECT / AUTO_RESOLVE / CONTEST / ESCALATE, with the hard
  ceiling gating every automated action and ESCALATE as an unscored fallback rather than
  an EV competitor
- RDR rule optimizer — full cost curve across candidate auto-resolution thresholds,
  capped at the hard ceiling
- CE3.0 qualification engine — deterministic, zero-ML rules for reason code 10.4,
  demonstrating the rule-engine pattern on a second reason code

**Deliberately not built, and why:**
- **Semantic entailment checking for the evidence draft** — the verifier catches
  fabricated citations, uncited claims, and assertions whose evidence type is absent,
  but not a claim that cites a real fact while overstating it. That needs a second-pass
  entailment check; the current scan is disclosed as a floor, not a proof.
- **Wiring the draft into the decision path** — `draft_contest_response()` is called by
  nothing in the EV pipeline. It stays a prototype until the entailment gap is closed.
- **Analyst review UI beyond the Streamlit pages here, Merchant Intelligence Hub,
  live continuous retraining** — explicitly Phase 3 / vision-slide items in the
  `buildathon.md`; not attempted here.
- **Multiple reason codes** — the whole point of scoping to 13.1 was to make one slice
  tractable and honest rather than five slices shallow.

## Requirements

Pinned in `requirements.txt`, installed into a local `.venv` via `make install`.

**Python 3.10–3.13.** That range is the pins, not a preference: numpy 2.1.3 requires
`>=3.10`, and numpy / pandas / scikit-learn / matplotlib all stop publishing wheels at
cp313. Loosening the pins to reach 3.14 would mean unpinning numpy, and every number in
this README rests on these exact versions — so we pin the interpreter instead. Reported
numbers were produced on 3.13. On 3.13, `shap==0.46.0` has no wheel and is built from
source, so a C toolchain is needed (`xcode-select --install` / `build-essential`);
`make doctor` says so explicitly if it's missing. On 3.12 every pin is a prebuilt wheel
and nothing compiles.

**macOS also needs `brew install libomp`** for XGBoost. `make install` warns before pip
runs and hard-fails after, with that exact command.

If you use pyenv or uv, `pyenv install 3.13` or `uv python install 3.13` gets you a
suitable interpreter; neither is required.
